# Flutter functional baseline and website mapping

The existing source was inspected before implementation; no files in `lib/`, platform projects or Flutter configuration were changed. The website is an adjacent application with durable server state.

| Existing Flutter source / behavior | Website equivalent and expansion |
|---|---|
| `features/auth/screens/role_select_screen.dart`, `login_screen.dart`, `state/auth_state.dart` | Real customer/provider/rider registration, login/logout, cookie sessions, protected admin bootstrap; explicit preview account selector |
| `features/customer/screens/customer_dashboard.dart` | Customer active/history/receipts, saved addresses, favourites, repeat bookings and guided tour |
| `features/customer/screens/request_laundry_flow.dart` | Guest-first service/location/review steps; legacy fixed services plus quick loads, quantities/kg, home visits, cleaning/custom budgets, photos and scheduling |
| `core/constants/app_constants.dart` | Preserved fixed service rates 500/700/1200/1500, pickup 150, delivery 150, express 300 and demo promo; all admin configurable. Maseno areas active; legacy Kisumu/Luanda are retained as data and can be added by admin |
| `features/customer/screens/order_tracking_screen.dart`, `models/order_model.dart`, `state/order_state.dart` | Full laundry stages including sorting/QC/dispatch; provider/rider assignment, PIN, bag verification, counts/weight, ETA, timeline, delivery/completion, cancellations/refunds and collected-clothes returns |
| `features/mama_fua/screens/mama_fua_dashboard.dart`, `order_processing_screen.dart` | Provider request queue, accept/decline, full processing, completed work and commission earnings; expanded verification, public profiles, individual/business/cleaning types, area/radius/availability and self transport |
| `features/rider/screens/rider_dashboard.dart`, `active_job_screen.dart` | Pickup/return trip queue, single active trip, assigned customer details, pickup PIN, bag checks, pickup/delivery completion and durable per-leg earnings |
| `features/admin/screens/admin_dashboard.dart` | Operational overview, providers/verification, users/rider approvals, bookings, assignment/reassignment, cancellation/refund records, payment records, pricing/packages, disputes, reviews and audit log |
| `models/notification_model.dart`, `state/notification_state.dart`, notifications screen | Persistent user-scoped in-app notifications, unread count, mark read/all; notifications generated by actual operational events |
| `services/interfaces/payment_service.dart`, `services/mock/mock_payment_service.dart`, `models/transaction_model.dart` | Modular demo/disabled/Swifta payments, server-only environment secrets, upfront/deposit/balance/pay-after, status polling, signed webhooks, receipts and settlement ledger |
| `services/interfaces/location_service.dart`, `services/mock/mock_location_service.dart`, `core/widgets/mock_map_view.dart` | Status/ETA and optional Google Maps search/location sharing, scoped phone and WhatsApp links; mock live GPS replaced with honest operational tracking |
| `state/tour_state.dart`, `tour_overlay_wrapper.dart`, `demo_role_switcher.dart`, `services/mock/mock_data.dart` | Six-step tour and explicit role demo, shared persistent local demonstration state, reset available to preview admin; sample identities/photography disclosed |
| `core/database/sqlite_service.dart` | SQLite on the API host with transactions/WAL/backup; session draft retention and previously viewed booking/history cache in the browser tab; the built public app shell works offline after its first successful load. Server transactions need connectivity and offline payments/status changes are blocked |

Additional customer features include actual verified-provider discovery, reviews tied to completed jobs, saved favourites, preferred-provider rebooking, custom job negotiation by acceptance, repeat request scheduling and student packages. The operational reports intentionally distinguish earned amounts from customer receipts and external payout/refund transfers.
